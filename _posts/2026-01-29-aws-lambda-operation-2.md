* AWS Lambda의 Python3.9 런타임 종료(EOL) 대응 과정에서, 다른 툴이나 자동화 없이 순수 AWS Console 상에서 코드를 작성하는 방식의 람다 개발 환경이 문제가 있다고 판단함.
* Console 기반에서 GIT + CLI 기반 개발환경으로 변경

* 하지만, 특정 함수 배포 시, 관련없는 다른 함수들이 같이 패키징되는 문제, CI/CD 미구축 등 개선해야 할 점이 아직도 남아있음

# 개요

## 지난 이야기 요약 - AWS Console 기반 개발의 문제점과 개선

<br>

지난 이야기 포스트: [AWS Lambda 개발환경 개선기 (1): 콘솔에서 탈출하다](/aws/2026/01/22/aws-lambda-operation.html)

<br>

포스팅 날짜로부터 한달 하고도 보름 전, Python3.9로 작성되어 있는 람다 함수의 Python 버전을 올리라는 AWS 권고에 대응을 하던 중, 작성된 코드들을 보고 기존의 람다 개발 환경은 리스크가 있다고 판단했다.
그 당시, 별개의 툴을 사용하지 않고, 순수 AWS Console에 들어가 직접 코드를 작성하고 deploy 버튼을 눌러 배포하는 방식이었는데, 이는 아래와 같은 문제점을 가지고 있었다.
* 개발/운영 분리가 되어 있지 않아 개발시 운영에 영향을 미칠 수 있다
* 코드 이력이 없어 누가 언제 이 코드를 작성했는지 알 수 없다.
* `requests`, `sqlalchemy` 같은 외부 모듈을 사용하려면 일일히 콘솔에서 Layer를 추가해야 한다. - 추가해야 할 모듈이 많아지면 관리하기가 심각하게 복잡해진다.

이런 이유로 나는 약 3주간의 기간을 걸쳐 개발환경을 **콘솔 기반에서 GIT + CLI 기반으로 전환을 했고**, 아래와 같이 개발환경에 대해 개선이 되었다.

* 이제 본인이 쓰고 있는 IDE로 직접 개발이 가능해졌다
* Git/Github 기반의 코드 이력이 생겨, 언제 어떻게 개발을 했는지 가능하다.
* 외부 모듈을 `pip`로 관리를 하게 함으로써, 일일히 마우스로 Layer를 추가할 필요가 없다.

## 1차 개선을 했지만...

그래도 여전히 문제는 남아있었다.

* 특정 함수 배포 시, 해당 함수와 관련없는 함수들의 코드 까지 전부 패키징이 된다.
* 여전히 노트북에서 커맨드 쳐서 배포해야 하는 수동배포

비록 초기 개선 당시, 연말에 정리해야 할 업무들이 많아 이 부분들 까지 세심하기 살펴보지 못했지만, 그냥 지나치기에는 비중이 큰 문제들이었기에 이 문제들 까지 깔끔하게 해결하는 시간을 가지기로 했다.

# 본론

## 배포 시, 관련없는 코드까지 패키징되는 문제

### 문제점

당시, 코드 패키징을 담당했던 스크립트 `package.sh` 는 Repo에 있는 모든 코드들을 전부 패키징하는 로직을 가지고 있었다. 초기에는 문제가 되지 않으나, 세월이 지나고 여러 개발자들을 거치게 되면 코드량이 비대하게 많아질 텐데, 이때 여기에서 치명적인 문제가 발생한다. **람다 함수는 작성할 수 있는 코드 량이 정해져 있기 때문이디.** Lambda의 코드 최대 용량은 비압축 기준 250MB, 압축 기준 50MB 이다. 따라서 이 정해진 용량 이상의 코드가 올라오면, 더이상의 배포가 진행되지 않는다.
